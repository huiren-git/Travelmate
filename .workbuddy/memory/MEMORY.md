## 快照数据模型（checkpoint.db）
- `GET /api/v1/sessions/{id}/snapshot` 响应：`data.state.blackboard` = 完整 `TravelAgentState` 的 JSON（`_jsonable(values)`）。
- 行程在 `blackboard.daily_itinerary`（`DayPlan[]`），支出在 `blackboard.budget`（`BudgetDetail`，`detail` 只有 transport/hotel/food/tickets 类目总额，无逐日/逐笔）。
- **关键坑（已修复 2026-08-18）**：`messages` channel 原本全程只写 1 次（仅初始 human），AI 对话没落库。现已改：`validator_node` 在每个 `is_finished` 轮重新生成 `summary_text` 并 `update["messages"]=[AIMessage(content=summary_text)]`（去掉跨轮守卫，靠 `validator_router` 的 is_finished→__end__ 保证每轮一次）。supervisor `__end__` 追问路径本就返回 AIMessage。故 snapshot 的 `messages` 现可含多轮 human+ai。前端 `/chat` 已在 `useChatPageState` 加 hydrate（选中会话调 `fetchSessionSnapshot`，`messagesFromBlackboard` 映射回 `ChatMessage[]`，并用 `adaptGeneratedTripPlan({values:blackboard})` 同步恢复行程面板）。
- checkpoint BLOB 为 msgpack 编码（含 LangChain 对象 reviver）；同步读取用 `SqliteSaver.get_tuple(config).checkpoint["channel_values"]`（注：该版本 sync saver 无 `get_state`，有 `get_tuple`）。

## REPLAN 作用域机制（2026-08-22 落地）
- REPLAN 新增"作用域三桶"：locked（已发生/进行中）、preserved（未来但本轮不在授权范围）、editable（本轮授权可改）。只有 editable 交 LLM 重写，其余两桶原样 merge 回填（保 image_url/cost 全字段）。
- 核心设计：`_replan_payload`（给 LLM 的可编辑区）与 `_merge_replan_itinerary`（回填）**共用 `_is_locked_item(day,item,current_dt,scope)`**——scope 非 None 时"作用域外的未来项"也判 locked，两侧自动同时生效。
- 作用域三级收敛（`_resolve_replan_scope`）：item（活动名≥3字子串命中）→ day（相对日/第N天/M月D日；用"行程/安排/计划"标记词区分"明天的行程"是目标而"今天太累了"是原因）→ all（兜底=旧行为）。
- 致命根因（已修）：旧 REPLAN 时用户原话**从不进 prompt**（`_state_payload` 无 user_message key），LLM 靠记忆相似度回捞猜测→"重新生成而非修改"。现已加 `user_instruction` 进 payload。
- 时区坑（已修）：`_parse_current_datetime` 对 `...Z`(UTC) 入参先 `astimezone(UTC+8)` 再去时区；旧 `.replace(tzinfo=None)` 把 13:48 误读成 05:48→全行程解锁被重写。
- State 新增字段（不声明会 `InvalidUpdateError`）：`replan_scope`(itinerary_agent 写)、`replan_changes`(validator 写)；`summary_text` 语义放宽为"本轮回复文案"。
- validator 按 `plan_mode` 分叉：plan→行程总结语；replan→`_diff_itinerary(old=state.daily_itinerary,new=merged.daily_itinerary)` 生成"指令反馈语"，仍写 `summary_text`+AIMessage，前端零改动。
- `_normalize_itinerary` 已改按 raw_day.day 推 fallback_date（旧用 enumerate 下标，LLM 只返回 Day2 会串天）。
- **未做**：用户说"轻松一点"时 `structured_preferences.pace` 不自动更新，validator `_validate_itinerary` 仍按全局 pace 校验全程平均 item 数，可能与单日轻量化冲突；需另决策。
- replan 不重跑 budget_agent（`should_run_budget_after_itinerary` 限 plan 模式），换景点后 `budget.total` 陈旧（`enrich_itinerary_costs` 只补 item 级 cost）。
- 后端真实 import 需 langgraph；当前系统 python(D:\Python) 与 managed(3.13.12) 均未装，无法 import 实测，仅 py_compile + 引用定义核验通过。

## 行程时间起点机制（2026-08-22 落地）
- `start_date` 链路：前端 `StructuredPreferences.start_date`(string ISO 日期) → `preferences_parser` 透传(`date.fromisoformat` 校验) → `chat.py:_structured_state_values` 提到 dict 顶层 → `_initial_state` 写 state.start_date。前端计划清单 Modal 用原生 `<Input type="date">`(值即 YYYY-MM-DD，无 dayjs)。
- `get_start_date`(state_utils) 缺失/未传时回退 `date.today()+timedelta(days=1)`(明天)，不再用硬编码 `DEFAULT_START_DATE=date(2026,8,10)`(常量保留作极端兜底)。旧根因：chat.py:138 永远 None → 回退写死 8-10 → 必然过期。
- `_first_day_start_hint`(itinerary_agent)：今天出发→取整到当前整点(09:00~21:00)；非今天(含默认明天)→09:00。进 `_state_payload` 顶层 + system_prompt 规则约束 LLM"首日首个活动不得早于该值，当天不足2项则顺延次日"。
- current_time 仅"事后标 completed"，first_day_start_hint 才"事前规避过期"。空串日期后端 `str(...or "")` 处理为空不进 result，安全。
