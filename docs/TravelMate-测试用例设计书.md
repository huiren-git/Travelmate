# TravelMate 测试用例设计书

| 项目 | 内容 |
| --- | --- |
| 版本 | v1.0 |
| 测试对象 | TravelMate（FastAPI + React + LangGraph 多 Agent） |
| 覆盖范围 | 功能正确性、Agent 质量、性能成本、鲁棒性 |
| 测试层级 | 后端单元、后端接口、前端单元、端到端（E2E） |
| 测试原则 | 能下沉则下沉；涉及 SSE、状态持久化、真实模型或浏览器交互时走联调/E2E |

## 1. 测试目标

验证用户从输入旅行需求到获得、修改、保存行程的完整链路：

1. 正确处理自然语言与结构化输入，生成满足目的地、日期、人数、预算及偏好的行程。
2. 在预算超支、停止生成、外部服务异常和多轮改行程时，流程可解释、可恢复且数据不串会话。
3. 基于 Trace、Span 和 LLM 事件，稳定产出延迟、Token、成本、成功率与行程质量指标。
4. 通过可复现的固定用例集，形成可用于面试展示的质量报告。

## 2. 测试环境、数据与约定

### 2.1 环境

- 测试环境使用独立 SQLite 数据库、独立 Chroma/向量数据目录和独立用户 ID，禁止复用开发数据。
- 外部高德/天气接口：单元测试与接口异常测试使用 Mock；基准测试使用真实服务并记录执行时间。
- LLM：功能自动化用固定响应 Mock；性能、成本与 Agent 质量基准使用真实模型。
- 每条真实模型基准用例运行 3 次；报告输出均值、P50、P95 和失败率。

### 2.2 基准身份与固定时间

| 项目 | 取值 |
| --- | --- |
| 用户 A | `qa_user_a`，偏好：历史、美食、慢节奏、不吃海鲜 |
| 用户 B | `qa_user_b`，偏好：自然、紧凑行程 |
| 固定当前时间 | `2026-08-29 10:00:00`，Asia/Shanghai |
| 标准主用例 | 上海出发，北京 3 日，2 成人，预算 4,000 元，历史 + 美食，轻松 |

### 2.3 测试类型说明

| 类型 | 适用范围 | 典型工具/方式 |
| --- | --- | --- |
| 后端单元 | 纯函数、状态合并、成本计算、异常分支 | pytest + mock |
| 后端接口 | HTTP/SSE 契约、鉴权、数据库写入 | FastAPI TestClient/httpx |
| 前端单元 | SSE 解析、状态管理、组件渲染、错误提示 | Node test / Vitest（按项目现有测试框架） |
| 端到端测试 | 浏览器真实操作与前后端协作 | Playwright；真实模型场景单独标记 |

## 3. 质量门槛与度量口径

### 3.1 验收门槛

| 指标 | 门槛 | 说明 |
| --- | --- | --- |
| 自动化测试通过率 | 100% | 合入前必须满足 |
| 主流程 E2E 成功率 | >= 95% | 以固定基准集多次执行统计 |
| 硬约束满足率 | >= 90% | 见 3.3 |
| 预算中断恢复成功率 | 100% | 核心差异化能力 |
| 权限/参数错误码正确率 | 100% | 400/401/403/404/409 场景 |
| P95 首字响应（TTFT） | <= 2.5 s | 真实模型、同一网络环境 |
| P95 全链路完成时延 | <= 15 s | 正常 3 日行程基准 |

阈值是初始目标，不应用于伪造结论；面试材料中只填写实测日期、模型版本、样本量和真实结果。

### 3.2 指标公式

| 指标 | 公式/来源 |
| --- | --- |
| E2E 延迟 | `SSE done/stopped 时间 - HTTP 请求发出时间` |
| TTFT | `首个内容类 SSE 事件时间 - HTTP 请求发出时间` |
| P50/P95 | 成功样本延迟的 50/95 分位数 |
| 成功率 | `success Trace 数 / 总执行数` |
| Token | Trace 的 `total_tokens`；同时保存每个 LLM event 的输入/输出 Token |
| 单次成本 | `prompt_tokens × input_price + response_tokens × output_price` |
| 单成功行程成本 | `总模型成本 / 成功生成行程数` |
| 缓存收益 | `(未命中平均预取耗时 - 命中平均预取耗时) / 未命中平均预取耗时` |

模型单价必须从当期实际供应商价格表配置读取，并在结果报告中记录模型名、输入/输出单价和币种；不要把价格硬编码为结论。

### 3.3 Agent 质量评分

每次真实模型执行均进行硬规则检查。通过为 1，失败为 0：目的地正确、天数正确、预算处理正确、兴趣覆盖、同行人适配、日期合理、无日程冲突、结构可渲染、改行程范围正确。

`硬约束满足率 = 通过规则数 / 应检查规则数 × 100%`

另抽取每个场景至少 1 次结果，由两名评审独立按 1–5 分评分：可执行性、个性化、完整性、表达清晰度、安全性。分歧超过 1 分时复核，报告中同时给出平均分和样本数。

| F-13 | 后端接口 | 不存在 thread_id 调用 resume | `POST /chat/resume` | 返回 40401；不创建新状态 |
| F-14 | 后端接口 | 无中断状态的会话调用 resume | `POST /chat/resume` | 返回 40901；已有行程保持不变 |
| F-15 | 端到端测试 | 生成导致预算超支的高消费请求 | 等待预算中断，选择“压缩预算” | UI 出现决策卡；恢复后行程更新，预算不超过上限或明确说明原因 |

| F-22 | 后端接口 | 参考行程列表与采纳 SSE | 获取 list 后采纳 reference_id | 采纳结果写入指定 thread；事件完成；行程成本补全且 Trace 成功 |
| F-23 | 前端单元 | 参考行程采纳结果与行程 JSON | 调用前端适配器 | 正确生成卡片数据；缺失图片/可选字段不导致崩溃 |

### 4.2 Agent 质量

以下用例需要真实模型执行；同时标注自动化主测试层级。质量评分按第 3.3 节记录，不能仅以“模型返回了文本”判定通过。

| ID | 测试类型 | 场景与输入 | 自动检查/人工检查 | 通过标准 |
| --- | --- | --- | --- | --- |
| A-01 | 后端接口（真实模型） | 上海→北京，3 日，2 人，4,000 元，历史+美食，轻松 | 天数、兴趣、预算、日程结构 | 3 天完整；至少覆盖历史和美食；预算处理正确；硬规则 >= 90% |
| A-02 | 后端接口（真实模型） | 北京 3 日，800 元 | 预算可行性、超支中断 | 不编造“800 元全包豪华行程”；触发合理降级或超支确认 |
| A-03 | 端到端测试（真实模型） | 2 成人 1 儿童，上海迪士尼 2 日 | 人群适配、强度、费用 | 包含儿童适宜安排；避免过密；费用按人数计算 |
| A-04 | 后端接口（真实模型） | 老人出行，慢节奏，少步行，苏州 3 日 | 无障碍/节奏适配 | 日程不过早、换乘少、避免高强度连续活动 |
| A-05 | 后端接口（真实模型） | “我不吃海鲜，去厦门 2 天游” | 约束遵从 | 餐饮建议不包含海鲜主菜；若不确定，给出替代选择 |
| A-06 | 后端单元 + 后端接口（真实模型） | 已有 3 日行程，当前时间在第 1 天结束后，改第 3 天 | 锁定项与编辑范围 | 已完成/锁定项逐字段不变；目标日按请求更新 |
| A-07 | 后端接口（真实模型） | “第三天改去环球影城，其他不动” | 最小变更原则 | 非第三天内容的项目名、时间、成本、图片保持不变 |
| A-08 | 后端接口（真实模型） | “杭州周末两天，想轻松看看西湖” | 模糊需求澄清质量 | 只追问会实质改变方案的缺口；问题自然且不重复 |
| A-09 | 后端接口（真实模型） | 同时给出“低预算、五星酒店、包车、所有热门景点” | 冲突识别与解释 | 明确指出冲突，提出可选择的权衡，不默默忽略约束 |
| A-10 | 后端接口（真实模型） | 指定起点、终点和交通偏好 | 交通/行程逻辑 | 相邻活动无明显跨城或不合理时间冲突；交通建议符合偏好 |
| A-11 | 后端接口（真实模型） | 使用用户 A 与用户 B 的相反偏好生成同城行程 | 记忆隔离与个性化 | A/B 结果体现各自偏好；不得出现另一用户的偏好文本或数据 |
| A-12 | 后端接口（真实模型） | 参考行程采纳后：“把第二天改得更轻松” | 参考行程保真与增量修改 | 非目标天保留；目标天强度下降；输出结构合法 |

### 4.3 性能与成本

性能用例以真实 Trace 为准。单元/接口测试验证埋点正确性；性能基准测试在稳定网络、相同模型、相同数据条件下执行。

| ID | 测试类型 | 场景 | 步骤 | 预期结果/采集项 |
| --- | --- | --- | --- | --- |
| P-01 | 后端单元 | Trace/Span 上下文嵌套 | 启动 trace，嵌套 span，抛出异常 | 父子关系正确；异常 span 为 error；上下文最终被清理 |
| P-02 | 后端接口 | 标准主用例 Trace | 执行一次完整 SSE，查询 `/traces/{id}` | 有 trace、span 树、总耗时、LLM 事件和 Token；总 Token 与子事件可核对 |
| P-03 | 后端接口 | 首字响应 | 记录请求发送和首个内容事件时间 | 输出 TTFT；事件非空；记录 trace_id 供复盘 |
| P-04 | 端到端测试（真实模型） | 标准主用例 × 3 | 浏览器发起并等待完成 | 记录 E2E、TTFT、P50/P95、成功率、Token、单次成本 |
| P-05 | 后端接口（真实模型） | 1 日、3 日、7 日行程各 × 3 | 运行基准并导出 Trace | 比较天数对延迟、Token、成本的影响；不将不同模型混算 |
| P-06 | 后端接口 | 同城市同查询连续两次 | 首次后再次请求，读取 pre_fetcher span | 第二次缓存命中或耗时显著下降；数据仍符合当前用户请求 |
| P-07 | 后端单元 | 成本计算 | 给定输入/输出 Token 与单价 | 金额精度、币种转换、空 usage 处理正确；不得静默记为 0 |
| P-08 | 后端接口 | LLM 未返回 usage | Mock 无 usage 的模型响应 | Trace 标明 `usage_missing`/估算来源；报告不会把该样本当作精确成本 |
| P-09 | 后端接口 | 并发 5 个不同 thread 的标准请求 | 并发执行并查询 Trace | Trace/thread 不串；成功率、P95 与错误类型被记录 |
| P-10 | 前端单元 | Trace 列表和详情大文本 | 注入长 Prompt/Response 与多 Span | 默认截断/折叠；展开正确；不阻塞页面渲染 |

### 4.4 鲁棒性与安全性

| ID | 测试类型 | 场景 | 核心步骤 | 预期结果 |
| --- | --- | --- | --- | --- |
| R-01 | 后端单元 | 高德 POI/路线服务超时 | Mock timeout | 返回可控降级结果；不抛出未处理异常；span 标识错误/降级 |
| R-02 | 后端接口 | 天气服务异常 | 触发生成并 mock 外部 5xx | 行程主流程可按降级策略继续或返回统一 503；错误可追踪 |
| R-03 | 后端接口 | LLM 超时或不可用 | Mock provider timeout | 返回/推送可理解错误；Trace status=error/timeout；资源清理完成 |
| R-04 | 后端接口 | SSE 客户端中途断开 | 建连后断开连接 | 后台任务按策略取消或可恢复；不持续消耗模型 Token |
| R-05 | 后端接口 | 同一 thread 并发两次生成 | 并发 POST stream | 不发生状态覆盖；第二请求被拒绝、排队或有明确并发策略 |
| R-06 | 后端单元 | stop 与 done 竞争 | 同时模拟 stop 标志和完成事件 | 最终状态唯一且合理（cancelled 或 success）；不得双写/双发终止事件 |
| R-07 | 前端单元 | SSE 乱序、重复、未知事件 | 向解析器注入异常事件流 | 不崩溃；重复事件幂等；展示可理解错误/忽略未知事件 |
| R-08 | 端到端测试 | 刷新预算中断页面后继续 | 触发中断，浏览器刷新，选择决策 | 状态恢复；决策只执行一次；结果与未刷新流程一致 |
| R-09 | 后端接口 | SQL/提示注入式输入、超长 message | 发送特殊字符与超长文本 | 参数受限/安全处理；无 500、无数据泄露、无跨用户访问 |
| R-10 | 后端接口 | Trace 详情的隐私数据 | 以非所有者或普通用户访问 | 权限符合设计；Prompt/Response 至少不在未授权场景暴露 |
| R-11 | 后端接口 | SQLite 临时不可用/写入失败 | Mock DB 错误 | 返回统一服务错误；Trace 不出现半完成且误标 success 的记录 |
| R-12 | 后端单元 | 偏好删除后记忆检索 | 删除偏好并检索 | 失效偏好不参与生成；其他有效偏好仍可检索 |
| R-13 | 端到端测试 | 网络错误、500、超时反馈 | 拦截请求分别返回异常 | 页面不白屏；用户可重试；加载态与错误态正确切换 |
| R-14 | 后端接口 | 健康检查依赖异常 | 分别 mock SQLite/缓存不可用 | `/health` 清晰报告组件与总体状态；不误报健康 |

## 5. 自动化执行策略

1. **每次提交**：运行后端单元、后端接口和前端单元测试；Mock LLM/外部服务，要求稳定且快速。
2. **每日或合入主分支**：运行核心联调/E2E（F-04、F-15、F-17、F-21、R-08、R-13）。
3. **每次版本发布/面试数据更新**：运行 A-01 至 A-12 与 P-04/P-05，保留 Trace ID、原始结果、评分表及模型价格快照。
4. **失败复盘**：按 Trace ID 定位到具体 Span 与 LLM event，记录失败类别：输入校验、路由、外部依赖、模型输出、状态恢复、前端渲染。

### 工程案例：用 Trace 定位“不吃海鲜”约束失效

1. A-05 的 Supervisor Trace 已正确解析 `preference_updates.dietary_restriction=no_seafood`。
2. 同一 Trace 的 Itinerary Agent payload 却显示 `preferences={}`，最终状态 `structured_preferences=null`；约束在 Supervisor 路由到计划模式时未被写回状态。
3. Validator Trace 同样只收到空 preferences，因此无法拦截“海蛎煎（可要求不加海蛎）”之类的建议。
4. 修复后，A-05 的 Agent payload 已包含 `preferences.dietary_restriction=no_seafood`，输出改为明确非海鲜餐食；剩余 0/3 硬规则结果来自测试关键词将“非海鲜/不含海鲜”误判为命中，已作为测试判定器缺陷保留。
